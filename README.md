# DUO — списки и календарь для двух участников

Чистый самостоятельный шаблон, **без имён реальных людей, ключей, истории чьих-либо задач, адресов чужих проектов и привязки к аккаунтам автора**. Код на HTML/CSS/JavaScript без фреймворков, Node.js, npm и сборки. Существующие чужие сайты и базы не используются.

## Возможности

- Два участника с нейтральными названиями, которые можно изменить в интерфейсе.
- Отдельные списки задач, выполнение, удаление; общий список событий календаря.
- Локальное автосохранение, резервная копия JSON, импорт JSON.
- История последних 100 действий; серверная история при включённой синхронизации.
- Опционально: синхронизация через **свой отдельный проект Supabase**, пароли каждого участника, отзыв старых сеансов, ограничение попыток входа, защита таблиц RLS, контроль конфликтов версий.
- Адаптивный интерфейс: светлая и тёмная темы, выбор сохраняется в браузере. Без внешних библиотек и платных зависимостей.

**Проверьте ограничение:** две разные вкладки или устройства **не синхронизируются**, пока владелец не настроит собственный сервер. Для локального режима профиль и пароль не требуются: защита только средствами браузера, не для секретных данных на общем компьютере. Публичный GitHub Pages публикует исходники интерфейса, но не ваши личные списки из браузера и не пароли, если вы не добавляете их в репозиторий. 

## Запуск за 2 минуты — без сервера

1. Скачать ZIP этого репозитория и распаковать его.
2. Для работы модулей ES откройте сайт через любой статический веб-хостинг, например GitHub Pages (см. ниже); прямое открытие `file://index.html` в некоторых браузерах блокирует JavaScript-модули.
3. Пока `config.js` содержит `apiUrl: ''`, работает локальный режим без аккаунтов. Дела сохраняются в этом браузере. Экспортируйте JSON до очистки браузера.

## Публикация на GitHub Pages

1. Создайте **новый публичный репозиторий** GitHub в своей учётной записи. Добавьте все файлы шаблона в корень одним начальным коммитом. **Не копируйте историю или файлы чужого приватного проекта.**
2. Settings → Pages → Build and deployment → Deploy from a branch → Branch `main`, folder `/ (root)` → Save.
3. Откройте URL, который укажет GitHub Pages. У двух участников будет общая ссылка, но общие данные появятся лишь после настройки сервера. GitHub Pages поддерживает бесплатный хостинг публичного репозитория в рамках лимитов сервиса.
4. Не выкладывайте персональные данные и файлы резервных копий в GitHub: они доступны всем при публичном репозитории.

## Синхронизация и пароли — только свой Supabase

Использование Supabase **не обязательно**. Ни одна ссылка/переменная проекта не привязана к конкретному аккаунту. Порядок настройки:

1. Зарегистрируйте **собственный аккаунт** на [supabase.com](https://supabase.com) и создайте отдельный проект (не переносите старую БД или токены). Бесплатный тариф может иметь лимиты и при неактивности приостанавливать проект.
2. В Supabase Dashboard → SQL Editor запустите **только** `supabase/schema.sql`. Скрипт создаёт пустые таблицы и нейтральные профили `one`, `two`. Никаких чужих данных в них нет.
3. Разверните Edge Function из `supabase/functions/api/index.ts`, назовите **`api`**. Укажите `verify_jwt = false` (функция сама проверяет свои подписанные токены; это не Supabase Auth). Можно использовать Supabase CLI, установленный агентом, либо Dashboard.
4. В секреты **нового проекта** добавьте четыре переменные: `SESSION_SECRET` — случайная строка минимум 40 символов, `ALLOWED_ORIGIN` — ровно origin вашей страницы (например `https://yourusername.github.io`, **без** пути и завершающего `/`), `USER_ONE_PASSWORD` и `USER_TWO_PASSWORD` — два разных пароля минимум по 12 символов. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` Edge Functions получают из своего проекта, не вставляйте их в GitHub.
5. Откройте `config.js` и задайте `apiUrl: 'https://ВАШ-PROJECT-REF.supabase.co/functions/v1/api'`. Это **публичный адрес**, не секрет. Сохраните в собственном репозитории. Пароли и service-role туда не добавлять.
6. Откройте сайт. Войдите в один из двух профилей; проверьте добавление задачи, обновление страницы, второй браузер и календарь. Каждый участник может изменить свой пароль в настройках. **После смены пароля его исходное значение из хеша не восстановить.** Используйте менеджер паролей.
7. Проверьте защиту: неавторизованный запрос должен возвращать HTTP 401, обычные роли `anon` и `authenticated` не должны читать таблицы, при неверном пароле должен быть отказ. Дополнительные проверки перечислены в `AGENTS.md`.

### Что нельзя делать

- Не указывать URL чужого Supabase и не использовать уже существующие токены/пароли.
- Не копировать исходники чужого приватного приложения, Git-историю и резервные копии с людьми и событиями.
- Не размещать `SESSION_SECRET`, пароли, `SUPABASE_SERVICE_ROLE_KEY` или экспорт JSON в публичном репозитории.
- Не делать `verify_jwt = true` без перехода на полноценную Supabase Auth-схему: этот шаблон использует собственную авторизацию.
- Не объявлять «полностью закрытым» публичный сайт: исходники доступны, а защиту данных обеспечивает только сервер, если он настроен. Для изоляции токенов от других GitHub Pages одного аккаунта используйте отдельный домен/origin. Токен хранится в `sessionStorage` и удаляется при закрытии вкладки.
- Не отправлять один и тот же секрет обеим сторонам как персональный пароль: пароли разные.

## Структура

| Файл | Зачем |
|---|---|
| `index.html`, `styles.css`, `app.js`, `model.mjs` | Весь интерфейс, локальное сохранение и чистые операции над данными |
| `config.js` | Публичный URL **собственного** API (пустой по умолчанию) |
| `supabase/schema.sql` | Пустая база, RLS, история, попытки входа |
| `supabase/functions/api/index.ts` | Независимый API для собственного проекта |
| `supabase/config.toml` | Режим выполнения Edge Function |
| `tests/model.test.mjs` | Юнит-тесты без зависимостей (`node --test tests/model.test.mjs`) |
| `AGENTS.md` | Подробная инструкция для нейросети / Codex |

## Ограничения и статус

- Локальный режим протестирован автоматически; серверный режим содержит пример полноценного API, но **не развёрнут и не протестирован в чужом проекте**. Сервисные ключи пользователя не нужны для сборки шаблона.
- Изменения при конфликте версий не перетирают удалённые данные автоматически, но локальная версия требует ручного разрешения конфликта.
- Нет push-уведомлений/Telegram: интеграция исключена для уменьшения кода и отсутствия привязки к сторонним ботам.
- Резервные копии и состояние браузера следует считать конфиденциальными: локальное хранилище не шифруется.
- Скрипт SQL создаёт таблицы в `public` с RLS и без политик для клиента. API обращается к ним с service-role **только на сервере**.
- Тесты в `tests` не заменяют E2E настройки собственного Supabase.
